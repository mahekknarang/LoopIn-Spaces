PROJECT WALKTHROUGH

How it
works.

A plain-language guide to LoopIn: Spaces: what students see, what the admin does, and what the code is doing behind each feature.

01 · THE STUDENT JOURNEY

From finding a room to checking a decision

01

Choose a date and inspect the schedule

The booking page loads the rooms, the college timetable, and existing requests for the selected date. Green means open, red means a scheduled class, yellow means a request is waiting for review, purple means an admin approved a booking, and grey means special permission is needed.

02

Pick an open period and send your request

Choose a green period, choose the last period you need, and enter your name, contact, event name, and purpose. The server checks every required field, the date, the room, the timetable, approved bookings, and long breaks before saving anything.

03

Save the request ID

A successful request gets an ID such as BK-1024. The ID is created by looking for the largest existing number and adding one. Keep the ID: the public status page uses it to find your request without showing other students’ personal details.

04

Wait for the admin decision

A request starts as Pending. Pending requests appear yellow, but they do not reserve a room. An admin reviews the queue and either approves it or rejects it with a reason. If another request for the same time was approved first, the conflicting pending request is rejected.

02 · BOOKING RULES

How the app decides whether a slot is available

Classes and confirmed bookings block a slot

The availability check looks for a class in that room and weekday. It also looks for an approved booking on the exact date. If either one exists, the app refuses the request.

Pending requests are visible, but do not lock a room

More than one student may request the same pending slot. The admin’s approval is the point where the app checks again and gives the slot to one request. Other overlapping pending requests are then rejected.

Click a class to see its details

A red timetable cell opens a pop-up with the class label, room, date, and period. A restricted library cell opens a permission notice. Green open periods open the booking form.

A request cannot jump across a long break

The college has long breaks between some periods. Even if the periods before and after a break are both free, the app treats them as separate blocks. One booking cannot include both sides of a break.

Search rooms by their starting letters

The search box filters the venue list as you type. For example, typing “LAB” shows the lab venues. The date picker reloads the timetable and bookings for the date you selected.

XICA Library needs permission

The library stays unavailable to students unless an admin enables bookings after special permission is received. The app shows a clear notice when someone clicks its unavailable slot.

03 · FIND A ROOM FOR ME

How the best-fit finder works

Enter a date, group size, and number of periods. The app removes rooms that are too small, restricted, or occupied. It then looks for runs of consecutive free periods long enough for the event. Results are sorted from smaller capacity to larger capacity, so the smallest room that fits is highlighted first. This helps keep the auditorium and larger rooms available for bigger groups.

04 · THE ADMIN AREA

What each admin section is for

Requests

Shows pending requests in the order they arrived. The admin can approve or reject each one. Before approval, the server checks for a class or an already-approved booking again, so a stale screen cannot quietly create a clash.

Timetable

Shows the selected room and weekday. Admins can add, edit, or remove a class in one period, or import a timetable file. Importing replaces the saved timetable, so the admin should inspect the imported rows afterwards.

Venues

Stores each room’s name, type, capacity, and whether students can book it. Admins can add or edit rooms. A room with booking history cannot be deleted, because old requests need to remain linked to their venue.

History

Shows decided requests, newest first, including whether each was approved or rejected and the reason. This gives the admin a simple record of past decisions.

05 · TIMETABLE IMPORT AND OCR

How a timetable file becomes room entries

OCR means Optical Character Recognition: software looks at pixels in an image and tries to turn visible letters and numbers into text. LoopIn supports two different import paths:

Digital PDF: read its text and page positions

For the college’s digital timetable PDF, the Python library pdfplumber reads text words and where they sit on the first page. The importer uses the weekday heading, period times, semester labels, and column positions to work out which class belongs to which room and period. It is tailored to this college timetable layout; because it reads the PDF’s text layer and layout, this path is not OCR.

Image: recognize letters with OCR

For an image, the browser loads Tesseract.js, a JavaScript OCR tool. It recognizes text, then LoopIn tries to match each text line to a known room, weekday, time period, and class. Blurry images, unusual layouts, or text split across lines can lead to mistakes, so always review the imported timetable.

In short: OCR is the image-reading method. The PDF path reads selectable text from this college timetable’s known grid layout. A scanned PDF without a text layer may not work with the PDF path. Both paths save timetable rows; neither one can guarantee a perfect result from every file.

06 · DATA AND ADMIN LOGIN

Where the information lives

When Supabase is configured, Flask sends database requests from the server using the private Supabase key. The browser never receives that key. Without Supabase settings, the project falls back to JSON files in its local data folder; those files are useful for a local demo but may not persist on a hosted service after a restart.

venues

One row for each space: its name, type, capacity, and student-booking permission.

timetable

One row for each occupied room, weekday, time period, and class name.

bookings

One row for each request: ID, requester and contact, event, purpose, venue, date, status, and decision details.

booking_slots

One row per period in a booking, connected to the booking ID. This makes the periods easy to query and keeps related data linked.

The admin username and password come from server environment variables. A successful login creates a Flask session. Five wrong attempts from the same session trigger a one-minute wait. Supabase Row Level Security (RLS) blocks public table access; the app’s server uses its private key to read and write data.

07 · DATA STRUCTURES AND ALGORITHMS

Where the DSA appears in the code

DSA stands for Data Structures and Algorithms. These are the ways a program stores information and the steps it uses to find or organize that information.

Hash map · look up by key

A hash map stores a value under a key, like a room name or request ID. LoopIn builds Python dictionaries to find the room, class, or request directly instead of scanning every record each time.

Queue · first in, first out

A queue is a line: the first item added is the first item handled. LoopIn orders pending requests by creation time and places them in a linked queue for admin review. FIFO means First In, First Out.

Merge sort · organize lists

Merge sort splits a list into smaller parts, sorts those parts, and merges them back in order. LoopIn uses its own merge-sort implementation for slot order, request history, and room capacities.

Sliding window · find a continuous block

A sliding window checks a moving run of periods. It finds every block long enough for the event, resets when it meets a busy period, and also resets at the college’s long breaks.

Greedy best fit · use the smallest suitable room

A greedy choice makes the best immediate fit: among the available rooms, choose the smallest one with enough seats. It is a simple way to avoid suggesting a large room when a smaller one works.

Trie · search by the first letters

A trie is a tree of letters. The venue search follows the letters typed so far and returns room names that start with that prefix, such as “LAB”.

08 · TOOLS USED

The project stack, in simple terms

Python + Flask: runs the server, validates requests, applies booking rules, and serves the pages and API routes.

HTML, CSS, and JavaScript: build the pages, visual design, responsive layout, booking grid, forms, and browser interactions.

Supabase + PostgreSQL: holds organized, persistent tables for venues, timetable entries, bookings, and their time periods. Flask talks to it through the Supabase REST API.

pdfplumber: reads the digital PDF timetable’s text and positions.

Tesseract.js: recognizes text in an uploaded timetable image using OCR.

GitHub: stores the project source code and its change history.

Render: runs the deployed Flask web app on the internet.

A good mini-project explanation: “A student checks an available room and submits a request. Flask validates it, uses the timetable and booking data to prevent clashes, and saves the request. The admin reviews a first-come queue. Data Structures and Algorithms help search, sort, and find suitable room/time combinations.”
